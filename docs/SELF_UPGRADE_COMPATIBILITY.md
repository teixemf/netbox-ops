# Self-upgrade compatibility contract (schema 1)

The consumer is implemented in `netbox_ops/self_upgrade_manifest.py`. Release
tooling can use `encode_manifest(ReleaseRequirements(...))` to generate exactly
the same format that the consumer validates. This document defines the
interface; packaging and publishing are handled separately (#72).

For each stable release tag `vX.Y.Z`, publish these release assets:

- `netbox-ops-vX.Y.Z.tar.gz`
- `netbox-ops-vX.Y.Z.tar.gz.sha256`
- `netbox-ops-vX.Y.Z.compatibility.json`

The metadata asset is UTF-8 JSON, at most 16 KiB. For example:

```json
{
  "schema_version": 1,
  "version": "v0.6.0",
  "python_min": "3.12",
  "python_max_exclusive": null,
  "linux_families": ["debian", "rhel"],
  "layouts": ["archive"],
  "required_intermediates": []
}
```

All seven fields are required; duplicate keys, extra fields, invalid values,
unknown schemas and mismatched tags are rejected. Python versions are
major.minor strings; a null maximum means there is no declared upper bound.
The Linux family and layout arrays must be nonempty and contain unique
lowercase identifiers. `archive` identifies the recognized package installation
with the canonical launcher and virtual environment, not a Git checkout.

The intermediate array contains unique, ascending stable tags strictly older
than the target. Every checkpoint newer than the installed version is mandatory.
For example, a target of v0.8.0 declaring v0.6.0 and v0.7.0 requires both
steps from v0.5.0, but only v0.7.0 from v0.6.0. Every mandatory step must be
present in the official catalogue and independently compatible. The same
verified local environment must support every step.

A release with an official archive and checksum but no usable metadata stays
visible as unverified. Missing metadata, unknown layouts and unavailable
required releases never authorize an upgrade. Downgrades are blocked. A
compatible classification is read-only and does not authorize installation:
the installation flow must recheck the plan before any modification.

The examples are contract fixtures, not statements about a published release.
Release tooling must use the actual package version and supported requirements.
The producer can test its generated bytes by calling
`parse_manifest(data, Version.parse(tag))`.
